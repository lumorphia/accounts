# 監視と停止時の対応

web・DB・worker の生存は公開 `GET /api/health` で確認できる。利用者の ID や件数は返さない。機能が無効な worker は disabled、有効なのに心拍が無い・無効・2分以上前なら stale で503。健康な心拍はジョブの成功を保証しないため、滞留も別に確認する。

## 外からの監視

VPS の外の既存の Uptime Kuma 等に追加する。60秒ごとに `https://accounts.lumorphia.com/api/health` の HTTP 200 と `"ok":true` を確認し、3回連続の失敗・復旧を運営用の通知先に送る。トップと `/terms` の SSR、discovery と JWKS も5分ごとに確認する。証明書の期限14日前を通知する。最初に characters と accounts をそれぞれ停止し、2分後に503、再起動後に200と通知の復旧を実測する。試験は公開制限のある環境で行う。

## 処理の滞留

VPS の既存の監視から `docker/monitor/backlog.sh` を5分ごとに実行する。終了0は全項目0、終了1は滞留または問い合わせ失敗。監視の通知・復旧判定と1時間の同じ通知の抑制に接続する。利用者 ID・handle・画像キー・受信先は通知しない。

- 配送と画像削除: 15分より古い未完了を1件から通知。受信先・R2・機能フラグを確認し、失敗中の記録を消さない。
- 全体 / サービスの物理削除: 30日と1時間を超えたものを通知。worker の停止・バッチの遅れ・ロックを確認する。
- 確認済みキャラクター: 最後の取得から8日以上を通知。worker、取得元と共有 pacing を確認する。

`FEATURE_ACCOUNT_LIFECYCLE=0` は新規退会だけでなく配送・画像削除・purge も止める。公開後に止める場合は滞留が続くことを把握し、再開を運用記録に残す。未完了の outbox と削除要求には保管期限を設けず、再送を維持する。

## バックアップとリソース

backup コンテナの生存だけで成功とは扱わない。非公開バケットの新しい dump の時刻を別の監視から確認し、26時間以上新しいものが無ければ通知する。30日で消えることと、定期的な復元試験も確認する。

VPS は Prismtone の既存の CPU・メモリ・ディスク監視に accounts のコンテナを含める。ディスク85%、メモリ90%、CPU80%が10分継続を目安にする。DB のポートは監視のためにも公開しない。ログは Docker の10MB×3本で容量を抑える。

## Sentry

DSN は確認後に設定する。IP の保存を無効にし、[Developer の30日保存](https://sentry.zendesk.com/hc/en-us/articles/27118913621019-How-Long-Are-Errors-Events-Stored-in-Sentry)に合わせ、プランや実際のイベント種別の保存期間を確認する。90日になるプランへ変える前にはポリシーと公開判断を見直す。通常の Replay・Logs・Profiling は収集しない。SDK の除去と画面マスクを本番の試験で確認する。通知には認証情報・利用者情報・本文を含めず、Issue へのリンクで確認する。Prismtone の既存の Sentry 通知経路を使う場合は accounts のプロジェクトを明示的に追加する。

## 対応の順序

外部監視の失敗時は DNS / Cloudflare / Caddy、`dc ps`、DB、2 worker の心拍、滞留の順で確認する。ジョブを消して正常に見せない。DB や削除の問題では新規アクセスを制限し、復元時にも過去の退会や画像を復活させない。退会の詳細は [account-deletion.md](account-deletion.md)。
