# ADR-0015: 利用停止はアカウント単位で持ち、管理画面は二重に守って操作を記録する

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-11 |
| Deciders | t1nyb0x    |

## Context

運営の作業は、VPS で psql を叩くか、スクリプトを手で回すしかない (#39)。2026-10-11 の本番の確認でも、利用者の一覧、試しのアカウントの削除 (`DELETE FROM users`。アイコンの削除要求は積まれない)、OIDC のクライアントの登録 (運営者の Cookie を環境変数で渡す) をこの形で行った。記録が残らず、退会の手続きを通らない操作もできてしまう。

利用を止める操作も無い。`users.status` には `suspended` があり、`requireSession`・キャラクターの操作・ID トークンの発行は `suspended` を拒む。しかし `suspended` にする口は無く、各サービスに知らせる仕組みも無い。[計画](../plan.md) の §1 は「管理者、BAN はサービス」としていたが、Lumorphia の層で問題が起きたとき (なりすまし、他人のキャラクターの無断使用など、規約の §3) にアカウントを止める手段が要る。

管理者の判定は今 `users.role = 'admin'` で行っている (OIDC のクライアントの登録、旧台帳の取り込み、`requireAdmin`)。Prismtone は起動時に `ADMIN_USER_IDS` を `role` に書くため、env から外しても DB に `admin` が残る。DB の値を権限の根拠にすると、外した人の権限が黙って残る。

## Decision

### 利用停止はアカウント単位で Lumorphia が持つ

- [計画](../plan.md) の §1 の「管理者、BAN はサービス」を変える。アカウントの利用停止は Lumorphia が持つ。投稿の非表示・削除は各サービスに残す。投稿はサービスのデータで、Lumorphia は持たない。停止中にその人の投稿をどう見せるか (隠す、そのまま) も各サービスが決める
- 停止は `pending` と `active` の利用者に行う。退会中 (`deleted`) は停止しない。退会中に問題が見つかったら、本人が復旧したあとに止める
- 停止は利用者の行を `FOR UPDATE` し、同じトランザクションで次を確定する。`status = 'suspended'` と `suspended_at` (新しい列) の記録、セッションと OAuth のトークンの失効、各利用サービスへの知らせの投入 (ADR-0008 の `emit`)、監査の記録
- 解除は `suspended_at` を消し、規約の同意があれば `active`、無ければ `pending` に戻す。知らせも同じトランザクションで積む
- 停止中の本人は、ログイン・ダッシュボード・キャラクター・OIDC の認可を使えない (今の `requireSession`・`lumorphiaClaims` のまま)。handle は解放しない。キャラクターの再同期は止まる (今のジョブのまま)
- 停止中の本人は自分で退会できない (`requireActive`)。削除の申し出は問い合わせで受け、運営者が管理画面から退会の手続きに乗せる。このとき `suspended_at` を残したまま `deleted` にし、`restoreLumorphiaAccount` は `suspended_at` があれば復旧を拒む。退会で停止を抜けられないようにする
- 許可リストにいる運営者は停止できない (締め出しを防ぐ)

### サービスへの知らせ

- ADR-0008 の通知の `state` に `suspended` を足す。サービスごとの状態は `purged` > `deleted` > `suspended` > `active` の順に決める (`snapshot`)。`scope` は `account`
- サービスは `suspended` を受けたら、その sub のセッションを止め、ログインを拒む。`active` を受けたら再開する。投稿の扱いはサービスが決める
- 受け口の検証器は lumorphia/platform の `@lumorphia/auth-client` にある。今の検証器は `active`・`deleted`・`purged` 以外を拒むため、サービスが新しい版にする前に `suspended` を送ると、その sub の後の知らせが詰まる (ADR-0008 の「前の revision が届くまで後を送らない」)。そのため次の順に出す
  1. platform の検証器に `suspended` を足して出す
  2. 各サービスが新しい版にして受け口を作る (Prismtone は別の PR)
  3. accounts の停止の操作を開ける。それまでは `FEATURE_ACCOUNT_SUSPENSION=0` (既定) で停止の口を閉じる

### 管理画面の入口は二重に守る

- 置き場所は accounts の `/admin` (画面) と `/api/admin/*` (API)。退会・画像の削除・OIDC のクライアントの仕組みが accounts にあり、別のアプリにすると同じ処理を写すことになる
- 外側: Cloudflare Access で `/admin`・`/api/admin` を守り、外から届かないようにする。Access のパスの設定は間違えやすいので、外から `/admin` と `/api/admin/` が Access のログインへの 302 であることを Uptime Kuma で見張る (runbook/monitoring.md)
- 内側: アプリはリクエストのたびに、セッションの利用者の sub が env の許可リスト `ADMIN_SUBS` (カンマ区切りの UUID) にあり、かつ `active` であることを確かめる。DB の `role` は管理画面の判定に使わない
- `ADMIN_SUBS` が無い、または空なら管理画面は閉じる (404)。UUID でない値があれば起動を止める。空の値は空文字で届くため、読み込みで空を「誰もいない」として扱う
- 今 `role` で守っている操作 (OIDC のクライアントの登録、旧台帳の取り込み、`requireAdmin`) は、管理画面に移すときに許可リストに切り替える。移し終えたら `role` を権限に使わない。`administrator_cannot_delete` の判定も許可リストに寄せる

### 監査の記録を残す

- 管理画面の操作は、操作と同じトランザクションで `admin_audit_logs` に 1 行を書く。書けなければ操作も確定しない
- 持つもの: 誰が (運営者の sub)、いつ、何を (操作の種類)、誰に (対象の sub、またはクライアントの ID)、なぜ (理由。必須の自由記述)。利用者は sub だけで指し、メール・handle・表示名は書かない。理由にも個人の情報を書かない (画面に注意を出す)
- 利用者・クライアントへの FK は持たない。物理削除のあとも記録を残す
- アプリには追記の口だけを作り、更新・削除の口を作らない。期限切れの削除は worker が行う
- 保存期間は 1 年。ただし停止の記録は、その利用者の停止が続く間は残す。期間はポリシーの「保存と削除」に書く
- 一覧や検索などの読むだけの操作は記録しない。メールを見せる操作は記録する

### 時期

- accounts を外に開ける前に入れる。[公開判断](../runbook/release.md) の「公開を決める前に確認するもの」に、Access の 302 の監視、許可リストの確認、停止と解除の実測を足す

## Consequences

### 良い点

- Lumorphia の層の問題に、psql を使わずに手続きを通して対応できる。停止・解除・削除が退会と同じ配送で各サービスに届く
- 権限の根拠が env の許可リスト 1 か所になり、外せばすぐに入れなくなる
- 誰が何をしたかが、利用者の情報を最小にした形で残る

### 悪い点・受け入れるリスク

- 1 つのサービスでの問題でも、Lumorphia で止めると全サービスが止まる。サービスの中だけの問題は、これまでどおりサービスで扱う (規約の §3 の「各サービスの利用制限は原則としてそのサービス内で扱います」はそのまま)
- 停止の反映は非同期で、サービス側のセッションは知らせが届くまで生きる。ログイン時の UserInfo の確認 (ADR-0008) で、新しいログインはすぐに止まる
- Access のパスの設定を誤ると、外側の守りが黙って外れる。監視で拾い、内側の許可リストで止める
- 運営者が 1 人なので、監査の記録は自分の操作の控えに近い。改ざんを防ぐ仕組み (別の保存先への書き出しなど) は今は持たない

### 追従して必要になること

- lumorphia/platform: `@lumorphia/auth-client` の検証器と DB アダプターに `suspended` を足す (platform ADR-0006 の追記)
- Prismtone: `suspended` の受け口 (セッションの停止、ログインの拒否、投稿の見せ方)。別の PR
- 規約: §3 の利用制限に、Lumorphia アカウントの利用停止と、停止すると各サービスも使えなくなることを書く。ポリシー: 停止の状態と監査の記録の保存期間を書く。版を上げる
- runbook: 管理画面の使い方、`ADMIN_SUBS` の設定、Access の設定と監視

## Alternatives

- **今のとおり BAN はサービスだけに置く**: Lumorphia の層の問題 (なりすまし、他人のキャラクター) で、全サービスを個別に止めることになる。止め忘れたサービスから使い続けられる
- **`users.role = 'admin'` で判定する**: env から外しても DB に残る (Prismtone の `ADMIN_USER_IDS` の挙動)。DB を書き換えられたときに権限まで取られる
- **Cloudflare Access だけで守る**: パスの設定を誤ると誰でも入れる。アプリ側の確認を省く理由にならない
- **アプリで Access の JWT (`Cf-Access-Jwt-Assertion`) も検証する**: Access を通ったことをアプリが確かめられ、より強い。ただし Access のチームのドメインと aud の設定、鍵の取得が増える。まずは監視と許可リストで始め、必要になったら足す
- **管理画面を別のアプリにする**: 退会・画像の削除・クライアントの処理を写すか、内部 API を新しく作ることになる。運営者 1 人の規模に見合わない
- **停止を `status` だけで持つ**: 停止中に退会させると `deleted` で上書きされ、復旧で `active` に戻ってしまう。`suspended_at` を別に持って防ぐ
- **監査の記録をアプリのログに出す**: ログは常時保存しておらず (ポリシーの §5)、Sentry も 30 日で消える。操作と同じトランザクションで確定できない
