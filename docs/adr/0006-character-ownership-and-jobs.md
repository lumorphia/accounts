# ADR-0006: キャラクターの所有と再同期の要求を DB で確定する

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-07 |
| Deciders | t1nyb0x    |

## Context

A1.3b は Prismtone のキャラクター登録・本人確認・再同期を accounts に移す。登録件数、主キャラクター、確認済みの所有は同時操作でも保つ必要がある。手動再同期を要求してからジョブが動くまでに、同じ利用者がもう一度要求できる状態を残してはいけない。

## Decision

- `characters` を accounts の利用者に紐づける。利用者と Lodestone ID の組、利用者ごとの主キャラクター、確認済みの Lodestone ID に一意制約を置く。利用者の物理削除でキャラクターも消す。自己紹介の本文を保存する列は作らない。
- 利用者の行を `FOR UPDATE` でロックし、登録件数 (40)、主キャラクターの変更・削除・繰り上げ、トークン再発行、手動再同期を直列化する。サービス固有の投稿や OGP は扱わない。
- 確認トークンは `lumorphia-` と 8 桁の乱数、有効期間は 24 時間。取得後にもトークンと期限・利用者の状態を読み直す。再発行や削除の前に始めた取得結果は破棄する。長い文字列の一部を確認トークンとして扱わない。
- 本人確認の確定は利用者のロックに続いて Lodestone ID ごとの advisory lock を取る。異なる利用者による同時確認も直列化し、既存の確認済み所有者がいればエラーを記録する。一意制約も最後の防波堤にする。
- 確認済みキャラクターはトークンを削除してよい。再同期でトークンを要求せず、失敗しても確認済みを取り消さない。3 回連続で失敗すると古い可能性を示し、成功時にエラーと回数を消す。
- 再同期は利用者のロックを保持してから取得する。同期同士・削除・主キャラ変更の順序を保ち、古い取得結果による復活や失敗回数の上書きを避ける。この間、その利用者の変更は取得終了まで待つ。
- 手動再同期は最後の成功と最後の要求の両方から 24 時間空ける。`sync_requested_at` と pg-boss への投入は同じ DB トランザクションで確定させる。pg-boss の `db.executeSql` を Drizzle のトランザクションへ接続し、ライブラリが生成した投入 SQL のパラメーターをバインド値として渡す。
- キューは `exclusive` とキャラクター ID の `singletonKey` を使う。確認・同期ジョブの再試行は 0 回 (HTTP の再試行はアダプター内)。無効な利用者や削除されたキャラクターのジョブは読み直して skip する。
- 毎週月曜 04:00 (Asia/Tokyo) に、1 週間以上再同期していない確認済み・有効な利用者のキャラクターを 200 件ずつ読み、2 秒ずつずらして同期ジョブに分ける。
- worker は 1 つの LodestoneSource を確認と同期で共有する。`FEATURE_LODESTONE=0` のときは worker と cron を登録せず、待っている要求を消費しない。本番で取得を有効にするときは公式の HTTPS origin と識別用 User-Agent を必須にする。

## Consequences

複数の要求が同時に来ても件数と所有、主キャラクターの制約が保たれる。要求時刻だけが確定してジョブが失われる状態も避けられる。同期中の利用者の変更は外部取得を待つので、画面と API の接続で待ち時間を扱う。

この段階はドメインと永続ジョブまで。A1.3c では本人用の画面と API、サービス用の一覧、HTTPS の E2E を足す。その際、API と worker から別々の HTTP クライアントで取得して間隔を破らないよう、全体の取得経路をまとめる。退会通知の再送は A1.4 の専用の仕組みで扱う。
